### DEC-2026-05-21-004

- **Date:** 2026-05-21
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Move Pluggy transaction dedup from a PostgREST-based application-layer check to an authoritative server-side RPC (`upsert_pluggy_transactions(p_user_id, p_rows)` in migration 072) with two-level dedup keys — Level 1 = `(user_id, provider_transaction_id)`, Level 2 = a content key `(account_id, date, amount, LEFT(description,50), COALESCE(installment_number, -1))` — and treat any future `unique_violation` race with a refetch + `UPDATE` resiliency loop. Simultaneously, lock the categorizer to `temperature: 0` on every `client.messages.create` call (Sonnet single + Haiku batch + batch-of-1 delegated to Sonnet) and add a pre-batch dedup pass that collapses Step 3 edge-case candidates by `description` before sending to Claude, mirroring the same single answer across all duplicate copies. Add a test that verifies `temperature: 0` is passed through to all 3 categorizer code paths so a future PR cannot silently remove it.
- **Context:** Closes #519 (sync duplicated future installments for users with >1000 txns because the PostgREST dedup hit the 1000-row implicit cap and went blind — confirmed in prod 2026-05-20 with Lara and Augusto) and #518 (Claude returned divergent flow_type/category for duplicate descriptions in the same batch because temperature was unset and there was no intra-batch dedup, so score and DRE were stochastic). The two bugs compounded: #519 created the duplicates and #518 amplified the damage by categorizing them inconsistently. The fix moves the dedup to the database (no cap) and removes the randomness source.
- **Alternatives:** Raise the PostgREST `Range` header to >1000 (still fragile, future-bound); keep dedup in application code but paginate manually; rely on a future SQL unique index alone without the RPC (loses intra-batch dedup).

### DEC-2026-05-21-005

- **Date:** 2026-05-21
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Remove the double-submit CSRF cookie from the mobile impersonation landing page (`/i/impersonate/[token]`) — Next 16 forbids `cookies().set()` inside a Server Component (it must run in a Server Action or Route Handler) — and rely on the three remaining defense layers: (1) 16-byte hex nonce in the URL path (attacker needs the exact value); (2) 6-digit pairing code with max 3 attempts (second factor); (3) `Sec-Fetch-Site != cross-site` check in the verify route (blocks cross-origin POSTs).
- **Context:** PR #521 had set the CSRF cookie defensively as a fourth layer; production traffic immediately hit `Error: Cookies can only be modified in a Server Action or Route Handler` and returned 500. Equivalent CSRF protection survives via the three existing layers, so the structurally-impossible cookie is removed rather than restructured around.
- **Alternatives:** Restructure the landing as a Route Handler that issues a redirect (heavier rewrite); set the CSRF cookie from a client component after hydration (defeats httpOnly); downgrade Next.js to keep the pre-16 behavior.
- **Made by:** Human (Luan Sena) + Agent (Claude Opus 4.7)
- **Source:** PR #525 / commit 827385a

### DEC-2026-05-21-006

- **Date:** 2026-05-21
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Treat `flow_type` direction as a **structural invariant** enforced at multiple layers, not just a categorizer hint: (1) `getFlowType` gains an optional `description` parameter and overrides credit transactions whose description matches the income regex (juros/rendimentos/dividendos/JCP) or whose base category is `tax` (interpreting it as restitution) to force `income`; (2) `finalizeFlowTypes` in the categorization pipeline post-processes `category_sub` coherence (`pro_labore` → income only when type=credit, `internal_transfer`/`pix_own_account`/`entre_contas` → transfer); (3) migration 074 mirrors the TS rules into the SQL `get_flow_type` and adds `backfill_flow_type_corrections(p_dry_run)`; (4) **migration 075** adds a `BEFORE INSERT` trigger `transactions_auto_flow_type` that auto-populates `flow_type` when NULL — structural defense against any future manual import script (e.g., `import-item.mjs`) bypassing the TS pipeline; (5) skill gets new rules A24/A25/A26 to detect each class. A26 is later made type-aware (income only on credit) and a structural guard `type='debit' AND base='income' → expense` is added (PR #536) because Pluggy occasionally categorizes things like "COBRANCA CORRETAGEM CRIPTOATIVO" as Receita on debit transactions.
- **Context:** Audit on 2026-05-21 (post-duplicate-cleanup) revealed 413 P0 transactions in 8 active users where `type=credit` had `flow_type=expense/tax` — pre-existing bug masked while duplicates were the louder noise. The pipeline already marked `category_sub` correctly but derived `flow_type` from a `category` table that had inverted senses for income-like categories. Defense in the trigger is non-negotiable because import scripts and direct writes exist and will exist.
- **Alternatives:** Patch only `getFlowType` and ignore the import scripts; remove `flow_type` as a column and derive it on read (massive rewrite + scoring slowdown); enforce via CHECK constraint instead of trigger (cannot reference computed values like description regex from a CHECK).
- **Made by:** Human (Luan Sena) + Agent (Claude Opus 4.7)

### DEC-2026-05-21-008

- **Date:** 2026-05-21
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Resolve issue #527 (refunds counted incorrectly in score and DRE) with a **5-layer refund-pairing system**: L1 pipeline (`applyRefundPairing()` Step 1.7 between cross-document and Pluggy) — detect refunds, query candidate purchases for the affected `account_id` + amount + 90/180-day window, mark 1-match pairs as `flow_type='transfer'` + `category_sub='refund_paired:<original>'` (both refund AND original purchase), 0-or-many matches as `refund_unpaired`; L2 TS helpers `detectRefund()` (Detector 1 = description: estorno/devolução/refund/CANC COMPRA/Crédito de; Detector 2 = credit_card disguised: `type=credit` on `account_type='credit_card'` excluding cashback and bill payment); L3 SQL function `is_refund()` (immutable, mirrors TS) + updated `transactions_auto_flow_type` trigger calling it before `get_flow_type`; L4 RPC backfill `pair_refunds_with_purchases(p_dry_run)` with `data_protection_log` audit + `ScoreRecalcRequested` emission; L5 skill rules A27/A28 as regression checks. Required `PipelineTransaction.account_id` becomes mandatory (orphans skipped from detector). 63 unit tests cover positives/negatives/pairing edge cases.
- **Context:** Audit 2026-05-21 identified refunds entering the app as either expense or income — both wrong. The credit-card-disguised case is particularly hard because Pluggy returns refunds with the merchant name as description (no "estorno" string) and `type=credit` in a credit-card account — visually indistinguishable from a normal purchase. The 5-layer defense ensures the same logic survives in TS pipeline, SQL trigger, and standalone backfill RPC; the skill ensures regressions are caught. Prod impact: 276 transactions corrected across 11 users (97 paired, 155 unpaired, 24 ambiguous), A27/A28 = 0 post-execute.
- **Alternatives:** Detect refunds only in TS pipeline (loses defense against import scripts); rely solely on description-based detection (misses credit-card disguised); skip auto-pairing and mark all refunds as `refund_unpaired` (loses precision in DRE).
