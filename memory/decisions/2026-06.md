### DEC-2026-06-01-001

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Calibrate two `finanfix-audit` rules after the 2026-06-01 run flagged them as false positives. **A36** (avg_monthly_expense divergence): Batch 4 SQL now uses `calculated_at - 365 dias` as the `date_from` argument to `get_avg_monthly_expense`, mirroring the orchestrator (`orchestrator.ts:402-437`) — the previous use of `CURRENT_DATE` produced a ~10% natural window drift on recent scores with high expenses, generating false P0s. **S10** (excluded-pattern regression): condition rewritten from `~* 'ifood'` to `(~* 'ifood' AND NOT ~* 'ifood.*club')`, since PostgreSQL POSIX regex does not support the `/ifood(?!.*club)/i` negative lookahead used in `excluded-patterns.ts`. The `NOT ~* 'ifood.*club'` clause is the correct equivalent and lets legitimate iFood Club subscription signatures survive.
- **Context:** False positives in P0 alarms are the worst failure mode for the auto-remediation routine wired up in [[dec-2026-05-31-001]] — they consume the Stage 2 capacity on non-bugs and reconditions the reader to skim red. Aligning the audit SQL with the production code (`orchestrator.ts`, `excluded-patterns.ts`) makes the audit a literal mirror of runtime rather than a parallel implementation, which is the same single-source pattern established in [[dec-2026-05-28-001]]. No production code changes — calibration of the detector only.
- **Alternatives:** Mark both hits as known-acceptable noise without changing the rules (recurs daily, drowns real signals — the problem [[dec-2026-05-27-005]] addressed for the broader rule set); rewrite `excluded-patterns.ts` to drop the lookahead so a simpler regex could be shared (changes production behavior to fit the audit, wrong direction); use `CURRENT_DATE` everywhere including the orchestrator (introduces real window drift in scoring, not just in audit).

### DEC-2026-06-01-004

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Anchor "current month" computation in BRT (America/São_Paulo) across the dashboard signal pipeline, with `computePeriodRange` extracted as a pure function and `buildSignals` accepting an injectable `now`. Adds `DerivedSignals.currentMonthKey` / `brtDayOfMonth`, a 3-state fallback for the categories chart (current month / previous month / empty) with a dynamic title ("Para onde foi seu dinheiro em {mês}"), and a read-time start-of-month grace that suppresses the "income fell" insight on both the dashboard `general` slot and `/diagnostico` `pillar_renda`. Backfilled with deterministic tests across `computePeriodRange`, grace, `buildCategoryGroups`, `buildSignals` (also fixes date fragility in pre-existing suites that crossed the month boundary).
- **Context:** Vercel runs UTC. From ~21h BRT on the last day of the month, the server-side "current month" had already rolled forward while the user's calendar still showed the previous month — so the dashboard appeared zeroed (no income, no expense, empty categories chart) and the income-trend signal misfired as "income fell 100%". The fix is structural: timezone is a property of the domain (BRT is the user's truth), not of the runtime, and `now` is the kind of ambient dependency that must be injectable for tests to catch boundary regressions before they ship. Same single-source-of-truth posture as [[dec-2026-05-13-001]] and the period-flow RPCs — read paths must agree with write paths on what "this month" means.
- **Alternatives:** Force the Vercel runtime to São_Paulo timezone (leaks a deployment concern into business logic and breaks if a future host runs a different TZ); use `CURRENT_DATE` at the DB layer only (still drifts in TS code paths that compute month boundaries, and `CURRENT_DATE` is itself UTC on the host); suppress the income insight unconditionally on day 1 (kills a legitimate signal for the remaining 30 days of the month).

### DEC-2026-06-01-005

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Add a triage rule to the daily `finanfix-audit` routine: an **S6** hit (active pattern with empty 6-month history) that also appears under **S10** (excluded-pattern regression) is a structural false positive — "S6-credit-type" — and must not open a bug or trigger a migration. Reasoning: S6 queries only `type='debit'`, but recurring-income patterns (FII rendimentos, CRI coupons, salário) are `credit`-type by design and will never have a debit history. The 8 hits from the 2026-06-01 run (all pre-095 survivors also present in S10) fit this shape exactly. Fingerprint registered: `S6:match:debit-only-credit-type-false-positive`.
- **Context:** Continues the calibration discipline from [[dec-2026-06-01-001]] (which already aligned A36 + S10 with the production code) — the audit must be a literal mirror of the runtime's pattern semantics, not a parallel implementation that fires on type-class mismatches. Without this triage rule, the daily P0 channel keeps absorbing 8 false alarms that would re-condition the reader to skim red, the exact failure mode [[dec-2026-05-27-005]] worked to prevent and that the C-level Slack rewrite in [[dec-2026-06-01-002]] depends on.
- **Alternatives:** Rewrite S6 to query `type IN ('debit','credit')` (changes the rule's semantics for the entire population, not just credit-type patterns — produces a different class of false positives because credit-type patterns legitimately have sparse histories); split S6 into separate debit and credit variants (doubles maintenance for a category the rule was never designed to cover); ignore the false positives silently without fingerprinting (loses the audit trail and reopens the bug on the next run).
