### DEC-2026-06-01-001

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Calibrate two `finanfix-audit` rules after the 2026-06-01 run flagged them as false positives. **A36** (avg_monthly_expense divergence): Batch 4 SQL now uses `calculated_at - 365 dias` as the `date_from` argument to `get_avg_monthly_expense`, mirroring the orchestrator (`orchestrator.ts:402-437`) — the previous use of `CURRENT_DATE` produced a ~10% natural window drift on recent scores with high expenses, generating false P0s. **S10** (excluded-pattern regression): condition rewritten from `~* 'ifood'` to `(~* 'ifood' AND NOT ~* 'ifood.*club')`, since PostgreSQL POSIX regex does not support the `/ifood(?!.*club)/i` negative lookahead used in `excluded-patterns.ts`. No production code changes — calibration of the detector only.
- **Alternatives:** Mark both hits as known-acceptable noise without changing the rules (recurs daily, drowns real signals — the problem [[dec-2026-05-27-005]] addressed for the broader rule set); rewrite `excluded-patterns.ts` to drop the lookahead so a simpler regex could be shared (changes production behavior to fit the audit, wrong direction); use `CURRENT_DATE` everywhere including the orchestrator (introduces real window drift in scoring, not just in audit).

### DEC-2026-06-01-005

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Add a triage rule to the daily `finanfix-audit` routine: an **S6** hit (active pattern with empty 6-month history) that also appears under **S10** (excluded-pattern regression) is a structural false positive — "S6-credit-type" — and must not open a bug or trigger a migration. Reasoning: S6 queries only `type='debit'`, but recurring-income patterns (FII rendimentos, CRI coupons, salário) are `credit`-type by design and will never have a debit history. The 8 hits from the 2026-06-01 run (all pre-095 survivors also present in S10) fit this shape exactly. Fingerprint registered: `S6:match:debit-only-credit-type-false-positive`.

- **Alternatives:** Rewrite S6 to query `type IN ('debit','credit')` (changes the rule's semantics for the entire population, not just credit-type patterns — produces a different class of false positives because credit-type patterns legitimately have sparse histories); split S6 into separate debit and credit variants (doubles maintenance for a category the rule was never designed to cover); ignore the false positives silently without fingerprinting (loses the audit trail and reopens the bug on the next run).

Single-helper + guard-at-every-entry-point keeps the rule from re-diverging.
- **Alternatives:** Keep extending the descriptor regex per failing merchant (whack-a-mole, never converges across banks); only filter at read-time and leave bad rows written (leaks into score/insights/WhatsApp even when hidden in the UI).
