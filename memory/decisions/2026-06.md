### DEC-2026-06-01-001

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Calibrate two `finanfix-audit` rules after the 2026-06-01 run flagged them as false positives. **A36** (avg_monthly_expense divergence): Batch 4 SQL now uses `calculated_at - 365 dias` as the `date_from` argument to `get_avg_monthly_expense`, mirroring the orchestrator (`orchestrator.ts:402-437`) — the previous use of `CURRENT_DATE` produced a ~10% natural window drift on recent scores with high expenses, generating false P0s. **S10** (excluded-pattern regression): condition rewritten from `~* 'ifood'` to `(~* 'ifood' AND NOT ~* 'ifood.*club')`, since PostgreSQL POSIX regex does not support the `/ifood(?!.*club)/i` negative lookahead used in `excluded-patterns.ts`. The `NOT ~* 'ifood.*club'` clause is the correct equivalent and lets legitimate iFood Club subscription signatures survive.
- **Context:** False positives in P0 alarms are the worst failure mode for the auto-remediation routine wired up in [[dec-2026-05-31-001]] — they consume the Stage 2 capacity on non-bugs and reconditions the reader to skim red. Aligning the audit SQL with the production code (`orchestrator.ts`, `excluded-patterns.ts`) makes the audit a literal mirror of runtime rather than a parallel implementation, which is the same single-source pattern established in [[dec-2026-05-28-001]]. No production code changes — calibration of the detector only.
- **Alternatives:** Mark both hits as known-acceptable noise without changing the rules (recurs daily, drowns real signals — the problem [[dec-2026-05-27-005]] addressed for the broader rule set); rewrite `excluded-patterns.ts` to drop the lookahead so a simpler regex could be shared (changes production behavior to fit the audit, wrong direction); use `CURRENT_DATE` everywhere including the orchestrator (introduces real window drift in scoring, not just in audit).

### DEC-2026-06-01-002

- **Date:** 2026-06-01
- **Project:** FINANFIX (paribali-labs/finanfix)
- **Decision:** Rewrite Stage 3 of the daily `audit-routine` prompt so the Slack post that lands in the channel is C-level: business-language headline, neutral/factual tone, no jargon at the top (rule codes, batch names, P0/P1, "auditoria", "falso positivo" are forbidden in the main message); technical detail moves into thread replies. - **Context:** The daily financial-data-health post that CEO/CTO read in the channel had been written in skill-internal language — readers could not parse parts of the message, so the routine's signal was effectively half-delivered. Splitting the audience (business in the post, technical in the thread) lets one routine serve both readers without sacrificing either. Continues the "Princípio da Ação" discipline from [[dec-2026-05-27-005]] at the presentation layer: only signals the reader can act on appear at the top.
- **Alternatives:** Keep the technical format and train readers to parse it (the conditioning that [[dec-2026-05-27-005]] explicitly works against); duplicate the routine into a "business" and "technical" variant (two routines drift apart over time); only post the business summary and drop the technical detail (loses the engineering audit trail that drives Stage 2 remediation).
